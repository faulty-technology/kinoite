# vLLM 0.31.0 on the FP8 27B, decode versus depth

## What was measured

On 2026-10-05 kyuz0 published `docker.io/kyuz0/vllm-therock-gfx1201:rocm7.14.1-torch2.11.0-vllm0.31.0`
(`sha256:3aff436e…`, also tagged `native-fp8` and `sha-2db18ad`). It is not
promoted to `latest` or `dev`. `vllm.container` pins `:latest`
(`sha256:55fa7796…`, built 2026-06-13), which reports itself as
`0.22.1rc1.dev499+g470229c37`.

**Arms.** Both arms ran in one window on 2026-10-09, under the shipped 250 W cap,
using the shipped `vllm-serve.sh` unchanged:

- `Qwen/Qwen3.8-27B-FP8`, TP=2
- MTP k=4 on `TRITON_ATTN`
- prefix caching with `mamba-cache-mode align`
- `--max-model-len 131072`, utilisation 0.80, `NCCL_PROTO=Simple`

The only difference was the image. The control, `:latest`, ran first on its
existing warm compile cache. The 0.31.0 arm got its own empty cache directory.

The 0.31.0 arm's first start died in the same cold-compile KV shortfall as
[runs/2026-09-18-vllm-0271-fp8-depth](2026-09-18-vllm-0271-fp8-depth.md): 4.74
GiB needed against 4.18 GiB available, with an estimated maximum length of
113,424. The second start served in 121 s.

## What it means

**vLLM 0.31.0 regresses decode at depth on this launcher, and badly.**

- Short prompts are unchanged: 58.5–59.4 ms per pass on both images.
- From 9,479 tokens down, every pass costs more. 0.31.0 runs at 1.31x the
  control's per-pass time at 9,479 tokens, 1.93x at 37,763 and 2.30x at 69,751.
- Acceptance is flat or slightly higher, so the drafter isn't the cause. It is
  the deep-context path of the target pass.
- It also yields a 12% smaller pool from the same utilisation.
- Not investigated: whether a different attention backend or a 0.31-specific
  flag recovers it.

**The 09-18 "falloff is better upstream" conclusion does not hold.** That run
compared 0.27.1 against the 08-30 figures of `:latest`, not a same-window
control. Today the same `:latest` image runs 59.02 / 67.20 / 91.63 / 119.50 ms
per pass, essentially 0.27.1's 59.81 / 67.59 / 92.24 / 120.21. Whatever improved
between 08-30 and 09-18 came from something other than the vLLM version, most
likely launcher changes made in between. The 0.27.1 arm was not re-run here.

Nothing is adopted. The `:latest` pin stays. The 0.31.0 image and its compile
cache (`~/.local/share/vllm/cache-v031`) remain on the box.
